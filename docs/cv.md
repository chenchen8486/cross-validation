# /cv — 独立 API 盲审交叉验证

通过外部独立 API（如 DeepSeek / Kimi）对技术内容进行盲审，评审结果与当前 Claude Code 会话物理隔离，解决单一 AI 模型长期使用导致的记忆衰退与注意力分散问题，实现真正的交叉验证。

**语言约束**：请在本命令的全部交互过程中优先使用中文，包括步骤说明、错误提示和最终展示给用户的文本。

**核心设计原则**：

- 加不加 `/cv`，Claude 理解用户请求、获取工程上下文的方式**完全一致**。
- `/cv` 不是另一个有规则约束的命令，而是**同一个请求，换一个纯净的回答者**。
- 不区分路径与自然语言、不预设文件数量上限、不绑定语言栈。Claude 自主决定需要读取什么。
- 唯一区别：当前 Claude 会话受历史记忆影响，而 `/cv` 调用外部独立 API，以零记忆视角给出复判。

---

## 模式判断

1. **如果为空、或以 `help`、`-h`、`--help` 开头** → 执行【帮助模式】
2. **如果 `$ARGUMENTS` 包含对话历史指代词，且未指定文件路径** → 执行【对话历史盲审模式】
3. **其他所有情况** → 执行【统一盲审模式】

**对话历史指代词**（满足任一即触发）：
`你刚才`、`你的回复`、`你的回答`、`你之前说`、`上面的回复`、`上面的回答`、`上文`、`上面说的`、`当前回复`、`刚才说的`、`刚才的回复`、`看看你说的`、`评审你`、`盲审你`。

**排除条件**（优先级更高，不触发本模式）：
- `$ARGUMENTS` 中明确包含文件路径特征（如 `src/`、`docs/`、`.py`、`.md`、盘符如 `C:` 等）→ 按文件评审处理。
- 当前对话中 Claude 尚未生成过任何回复 → 提示用户。

## 【帮助模式】

当 `$ARGUMENTS` 为空、或以 `help`、`-h`、`--help` 开头时，进入帮助模式。

1. **尝试读取外部帮助文档**：
   使用 `Read` 工具读取文件 `docs/cv_help.md`。
   - 如果 `Read` 成功：将其中的 Markdown 内容直接展示给用户（不要包裹在代码块中）。
   - 如果 `Read` 返回错误（文件未找到）：进入步骤 2。

2. **Fallback 内联帮助**（当外部文件不存在时展示）：

   ```
   # /cv 命令使用指南

   ## 核心定位
   /cv 与直接提问的区别仅在于回答者：
   - 直接提问：当前 Claude 回答（受历史上下文影响）
   - /cv：外部独立 API 回答（零记忆、纯净视角）

   ## 场景速查
   | 你想做什么 | 命令示例 |
   |:---|:---|
   | 评审单个文件 | `/cv 帮我看看 src/api.py 是否合理` |
   | 评审整个工程 | `/cv 审查当前工程的代码质量` |
   | 多轮闭环博弈 | `/cv_debate docs/requirement.md` |
   | 查看帮助 | `/cv help` |
   ```

   展示后结束。

## 【对话历史盲审模式】

当用户请求评审 Claude **在当前会话中刚刚生成的回复**时使用。此模式解决了一个真实痛点：用户想要另一个独立模型对同一段对话内容进行交叉验证，但 `/cv` 默认只接受文件输入。

### Step 1：提取对话历史

从当前 Claude Code 会话中，提取 **Claude 最近一次生成的完整回复内容**（排除系统消息、工具调用结果、以及用户自己的输入）。

**边界检查**：
- 如果当前对话中 Claude **尚未生成过任何回复**（例如用户首次输入就是 `/cv 你刚才说的`）：
  ```
  当前对话中暂未检测到需要评审的回复内容。
  请先用正常对话向 Claude 提问，获得回复后再使用 `/cv` 进行盲审。
  ```
  停止执行。

- 如果提取到的回复内容 **少于 50 个字符**（过短或无实质内容）：
  ```
  检测到的回复内容过短（仅 X 个字符），不足以进行有意义的盲审。
  请确保 Claude 已生成一段完整的技术回复后再试。
  ```
  停止执行。

### Step 2：准备待审文件

将提取到的回复内容写入 `temp/cv_conversation_audit.md`，格式如下：

```markdown
# 对话历史盲审（由 /cv 自动生成）

> 用户原始请求：[$ARGUMENTS]

> 上下文说明：以下内容是当前 Claude 会话中最近一次回复的完整文本。
> 外部独立评审模型对此内容一无所知，将以零记忆、无污染视角进行盲审。

---

[Claude 的完整回复内容]
```

若 `temp/cv_conversation_audit.md` 已存在，直接覆盖。

### Step 3：提取定向指令

从 `$ARGUMENTS` 中去除对话历史指代词后的剩余部分，作为**定向评审指令**。例如：

| 用户输入 | 指代词 | 定向指令 |
|:---|:---|:---|
| `/cv 你刚才的回复里，重点看看并发安全` | `你刚才的回复里，` | `重点看看并发安全` |
| `/cv 上面的回答有没有漏洞` | `上面的回答` | `有没有漏洞` |
| `/cv 你之前说的合理吗` | `你之前说的` | `合理吗` |

如果去除指代词后为空，则不传递 `--instruction` 参数。

### Step 4：前置依赖检查

与【统一盲审模式】Step 3 完全一致：

```bash
cv-review --help > /dev/null 2>&1 || echo "NOT_FOUND"
```

- 若输出包含 `NOT_FOUND`：展示安装/环境提示，停止执行。
- 若检查通过：继续 Step 5。

### Step 5：调用盲审

```bash
cv-review --file "temp/cv_conversation_audit.md" [<若定向指令非空> --instruction "<定向指令>"]
```

**引号安全处理**：若定向指令包含双引号 `"`，则不传递 `--instruction` 参数（用户请求已写入文件头部，reviewer 会看到）。

**错误处理**：与【统一盲审模式】Step 4 完全一致。

### Step 6：展示评审结果

将 `Bash` 的 stdout 内容完整展示给用户。在结果前加上标识：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
独立 API 盲审意见（针对当前对话回复，物理隔离）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[评审意见内容]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### Step 7：交互闭环

询问用户：

```
是否需要我根据以上盲审意见直接修改原回复涉及的相关文件？
   （回复"是"直接修改，回复"否"或忽略则结束）
```

- 若用户明确同意：使用 `Edit` 工具直接修改原文件，修改后向用户汇报变更点。
- 若用户拒绝或没有明确同意：结束，等待用户下一步指令。

> **注意**：此模式评审的是**对话文本**，而非磁盘文件。因此 Step 7 的"修改原文件"仅当盲审意见指向了工程中的具体文件时才适用。如果评审意见只涉及对话内容的表述问题，向用户说明"本次盲审仅涉及对话表述，无工程文件需要修改"。

## 【统一盲审模式】

### Step 1：理解用户请求并自主获取上下文

将 `$ARGUMENTS` 整体视为用户的自然语言请求。

请像处理普通对话问题一样，自主判断需要读取哪些文件、获取哪些上下文，才能完整理解并回应这个请求。

**没有任何额外约束**：
- 不限制文件数量
- 不限制语言栈或文件类型
- 不限制内容大小
- 不需要做"路径特征"判断

Claude 自行决定读取范围。如果用户明确提到了某个文件路径，那该文件通常是重点；如果用户问的是"工程整体"，则按需扫描核心文件。

### Step 2：准备待审内容

根据 Step 1 读取到的内容：

- **若涉及多个文件或需要聚合工程上下文**：
  使用 `Write` 工具将用户请求与文件内容聚合到 `temp/cv_intent_bundle.md`，格式如下：

  ```markdown
  # 工程文件汇总（由 /cv 自动生成）

  > 用户原始请求：[$ARGUMENTS]

  ---

  ## 文件：[相对路径]

  ```[语言标识]
  [文件内容]
  ```
  ```

  语言标识规则：`.py` → `python`，`.js` → `javascript`，`.ts` → `typescript`，`.java` → `java`，`.go` → `go`，`.rs` → `rust`，`.md` → `markdown`，其他 → 空或根据扩展名推断。

  若 `temp/cv_intent_bundle.md` 已存在，直接覆盖。

  **目标文件路径**记为 `temp/cv_intent_bundle.md`。

- **若仅涉及单个文件**：
  **目标文件路径**即为该文件路径，无需额外聚合。

### Step 3：前置依赖检查

在调用底层 CLI 之前，使用 `Bash` 验证 `cv-review` 是否可用：

```bash
cv-review --help > /dev/null 2>&1 || echo "NOT_FOUND"
```

- **如果输出包含 `NOT_FOUND` 或返回命令未找到错误**：
  向用户展示：
  ```
  未检测到 cv-review 命令。可能的原因：
    1. 未在虚拟环境中安装：pip install -e ".[dev,anthropic]"
    2. 虚拟环境未激活（如 conda activate Chen）
    3. 安装目录的 Scripts/ 或 bin/ 未加入系统 PATH

  请先在项目根目录执行以下诊断命令定位问题：
     cv-review doctor
  ```
  停止执行。

- **如果检查通过**：继续执行 Step 4。

### Step 4：调用盲审

组装命令并调用底层 `cv-review` CLI。

**引号安全处理**：
检查 `$ARGUMENTS` 是否包含双引号 `"`。若包含，为避免 Shell 解析错误，**不传递 `--instruction` 参数**（用户请求已写入聚合文件首部，reviewer 会看到）。

**执行命令**：

```bash
cv-review --file "<目标文件路径>" [<若 $ARGUMENTS 不含双引号> --instruction "<$ARGUMENTS>"]
```

**错误处理**：
- 如果返回码为 0：继续 Step 5。
- 如果返回码非 0：
  1. 将 stderr 内容完整展示给用户。
  2. 如果 stderr 包含 "API"、"认证"、"密钥"、"Authentication"、"Key" 等字样：提示用户检查环境变量是否已正确配置。
  3. 如果 stderr 包含 "文件未找到"、"FileNotFoundError"：提示用户检查文件路径。
  4. 否则：提示用户检查网络连接，或尝试带上 `-v` 参数查看详细日志。
  5. 停止执行。

### Step 5：展示评审结果

将 `Bash` 的 stdout 内容完整展示给用户。在结果前加上标识：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
独立 API 盲审意见（与当前会话物理隔离）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[评审意见内容]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### Step 6：交互闭环

询问用户：

```
是否需要我根据以上盲审意见直接修改相关文件？
   （回复"是"直接修改，回复"否"或忽略则结束）
```

- 若用户明确同意（回复包含"是"/"yes"/"y"/"好"/"改"等）：使用 `Edit` 工具直接修改原文件，修改后向用户汇报变更点。
- 若用户拒绝或没有明确同意：结束，等待用户下一步指令。

## 路径兼容性处理规范

在执行过程中，特别注意路径的跨平台兼容性：

1. **接收阶段**：无论用户输入什么路径格式（`/`、 `\`、 `//`、 `\\`、 带盘符、不带盘符），都原样保留传递给 `Read` 和 `Bash`。
2. **验证阶段**：始终使用 `Read` 工具验证路径是否存在。`Read` 工具本身具备跨平台路径解析能力。
3. **失败处理**：只要 `Read` 返回"文件未找到"或类似错误，**绝不要猜测路径或自动修正**，必须向用户明确报告并请求重新输入。
4. **传递阶段**：在组装 `Bash` 命令时，路径必须用**双引号 `"`** 包裹，防止空格或特殊字符导致解析错误。
5. **展示阶段**：向用户展示路径时，优先展示**绝对路径**（如果 `Read` 成功，可以从结果中得知实际解析后的绝对路径），让用户明确知道操作的是哪个文件。
6. **盘符兼容性**：Windows 路径的盘符大小写不敏感（`C:` 与 `c:` 等价），且支持混合分隔符。底层 `pathlib.Path` 会自动标准化，无需在提示词层做额外处理。
